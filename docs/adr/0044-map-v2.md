# ADR-0044: Map v2, an interactive map that can show data

- Status: **Proposed** (IND-228, design only; nothing here is built)
- Date: 2026-10-27
- Deciders: Jian (owner)
- Relates to: ADR-0004 (pre-built shell, no Node), ADR-0038 (CSP), ADR-0042 (lazy modules and the size
  budget), ADR-0039 (module components), ADR-0010 (per-session state); the `Map` component (G5)

## Context

The request reads "a native interactive Map component". One already exists: `indah.Map`, a Leaflet map
(`frontend/src/Map.svelte`, lazy module `src/indah/static/map.js`, 43.5 KB gzip against a 50 KB budget).
So this ADR is about what `Map` lacks, not about adding a first map. The trigger is the GRC demo
(`examples/grc_map.py`), which does not use `Map` at all: it draws a matplotlib figure and shows it as a
`Plot` image. Both facts matter, so the investigation comes first.

### What `Map` does today

- Raster tiles from `tile_url` (default `tile.openstreetmap.org`), fetched by the **viewer's browser**;
  the host is added to the CSP `img-src` by `register_img_host` (ADR-0038).
- Reactive `center`, `zoom`, `markers`, `polygons`, `polylines`. Vector layers, per-item `color`,
  `fillOpacity`, `label`. Python can "fly to"; the viewer's pan and zoom never come back.
- Not there: GeoJSON input, a value-to-colour scale or legend (choropleth), hover or tooltip content,
  click or selection events to Python, fit-to-bounds, a layer toggle, dark-mode tiles, the Studio colour
  tokens (a polygon's colour is whatever string the app passes), a no-tiles mode (blank background).

### Screenshot analysis of `grc_map` (2026-10-27, desktop 1280 px and phone 390 px)

Run locally with `examples/grc_map.py`, 2025 selected. The map is a 6 x 4.6 inch matplotlib figure at
150 dpi, rasterised to PNG, in a `Card`. What looks wrong:

1. **It is a picture.** No hover, no tooltip, no zoom, no click. A user cannot ask "which division is
   this?"; the table beside it is the only way to read a value, and the two are not linked.
2. **Colourbar ticks collide.** `100000120000140000160000180000` runs together; no thousands separator, and
   the font is large relative to the bar. This is the single most visible defect.
3. **Text is baked into pixels.** The title, tick labels and the source line scale with the image: on the
   phone they shrink to about 5 px and are unreadable, while the page text around them stays 16 px.
4. **It does not follow the theme.** The figure ground is a hard-coded `#fdf6ee`, visibly a different
   cream from the card (`--surface`), and it would not change in dark mode, which indah supports.
5. **The ramp is muddy.** A pale grey-green to near-black teal; mid values (60k to 120k) are
   hard to tell apart, and the "no data" beige sits at the light end of the same ramp, so it reads as
   "low" rather than "missing". The fixed global scale is a good decision; its rendering is not.
6. **Heavy black outlines at 0.5 pt** swamp the small central divisions and the islands, and the
   reclaimed-land edges on the west and east produce stray line artifacts.
7. **No geographic context** and no labels: nothing says which blob is Jurong or Tampines, and the
   figure is mostly empty space (the sea, the coloured outline) below the island for the colourbar.
8. **Layout.** 2,700 px of page for one idea; the figure alone is about 640 px tall on desktop and the
   Stat row duplicates what a legend and tooltip would show.

Points 1, 3, 4 and 7 are structural: they are what an image cannot be, and no matplotlib tuning fixes them.
Points 2, 5 and 6 are fixable in the example today (format ticks, a diverging-safe or viridis-like
ramp, a 0.2 pt white outline) and should be, as a cheap interim card, independent of the component work.

## Options

| Option | Fit | Cost | Verdict |
|--------|-----|------|---------|
| **A. Extend Leaflet** (keep `Map`, add GeoJSON, choropleth, events, tokens) | Leaflet 1.9 renders GeoJSON natively, SVG vectors are crisp, per-feature style and tooltips are built in, CSS themeable | no new dependency; `map.js` grows by a few KB; the 50 KB gzip budget has 6.5 KB of headroom | **Recommended** |
| B. MapLibre GL (vector tiles, WebGL) | Smooth zoom, vector basemaps, rotation, data-driven styling | about 220 to 280 KB gzip lazy module (5x Leaflet); needs WebGL (software-rendered in some Colab/remote browsers); web workers need `worker-src blob:` under strict CSP; vector tiles need a tile source (PMTiles or a hosted style), and glyph and sprite fetches | Defer. Revisit if a user needs a tiled basemap that is not raster, or tens of thousands of features |
| C. Raster tiles only (what we have) | Zero new code | No data layer | Already the base of A; it is the tile-source half, not a complete answer |
| D. Server-rendered image (status quo) | Works anywhere, no JS | The eight defects above | Keep as the documented fallback (`Plot`), not the answer |
| E. deck.gl, OpenLayers, d3-geo | d3-geo draws a choropleth in about 15 KB with no tiles | d3-geo is a projection library, so pan, zoom and attribution would be ours to build; OpenLayers is about 3x Leaflet; deck.gl needs WebGL | d3-geo is worth a spike only for a **tile-less** mode (see Q3) |

### Constraints and how A meets them

- **No Node at install or runtime (ADR-0004).** Leaflet is a `frontend/` devDependency, bundled at build
  time into the committed `map.js`; unchanged. MapLibre would also satisfy this, at 5x the size.
- **Size (ADR-0042).** `map.js` stays lazy; an app without a map downloads nothing. Raise `map_gzip_bytes`
  from 50,000 to 55,000 only if the slice needs it, and say so in the PR.
- **CSP strict (ADR-0038).** Leaflet vector layers are SVG with presentation attributes and inline
  `style` set through the CSSOM, which the e2e suite already passes under `csp="strict"` (the `gpx_viewer`
  and Studio pages). New work must not inject `<style>` elements (the nonce problem noted in
  `Map.svelte`); tooltips must use `textContent`, never HTML. MapLibre's blob workers would be a new
  CSP surface.
- **Colab and Runpod proxies.** The shell is served through the proxy, but tiles go **browser to tile
  host**, so they bypass it and work as long as the viewer's network can reach the host. Corporate or
  air-gapped viewers cannot; hence the tile-less mode (Q3). GeoJSON travels in the existing JSON patch
  channel, so size matters: a Singapore electoral map is about 100 KB raw. Large geometries need
  simplification before they are sent (Q4), and the proxy's SSE window-buffering (ADR-0002/0013) argues
  for sending geometry once as a static prop and only per-feature values reactively.
- **Licensing and attribution.** Leaflet is BSD-2, MapLibre BSD-3: both fine. The default OSM tiles are
  free for light use only (their policy forbids heavy or bulk use and requires attribution), so the
  public gallery must not rely on them at scale. Keep the attribution control on and non-removable
  when a tile layer is present; document alternatives (Carto basemaps, Stadia, Protomaps/PMTiles, a
  self-hosted tile server) and keep `tile_url` per deployment. Data layers carry their own `attribution`
  string (the ELD data is under the Singapore Open Data Licence). Never use `prettymaps` (AGPL), as the
  map-poster demo already decided.
- **Theming.** Fill colours come from a named scale (`sequential`, `diverging`, `categorical`, mapped to
  the Studio data-viz tokens, see ADR-0014) resolved **in the shell** from CSS variables, so a map
  re-colours in dark mode without a round trip. Tile layer: a CSS filter on the tile pane in dark mode
  (cheap, no second provider) or a `tile_url_dark` option.

## Recommendation

Adopt option A: grow `indah.Map` into a data map on Leaflet, and keep MapLibre as a named future option
behind the same Python API, so a user's code does not change if the engine does. Keep raster tiles
optional (`tile_url=None` draws on the theme background). Fix the three cheap defects of the GRC demo
now, then rebuild that demo on the new component as the proof.

### Proposed API (a sketch, not a contract)

```python
indah.Map(
    center=..., zoom=...,                  # as today
    geojson=fc,                            # a FeatureCollection (dict or path), static
    values=lambda: {"ANG MO KIO": 161499}, # reactive, feature id -> number
    id_property="name",                    # which GeoJSON property is the id
    scale=indah.Scale("sequential", domain=(20_000, 180_000), format=",.0f", no_data="neutral"),
    legend=True, tooltip="{name}: {value:,}",
    selected=sig, on_select=handler,       # click a feature, two-way like Select
    fit="data",                            # fit bounds to the geometry
    tile_url=None,
)
```

## Open questions

- Q1 Is dark mode via a CSS filter on OSM tiles acceptable, or should a dark provider be named?
- Q2 Does selection state live per session like other signals (yes by default, ADR-0010)?
- Q3 Tile-less default for the gallery, so the public demo never depends on OSM's usage policy?
- Q4 Where does simplification live: a Python helper, or a build-time script like `scripts/compile_grc_map_cache.py`?
- Q5 Raise the `map_gzip_bytes` budget, or find savings inside Leaflet (drop unused handlers)?
